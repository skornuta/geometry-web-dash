## 🔴 High Priority Gameplay & Physics Bugs

### [x] [BUG-01] Dual Mode Player 2 Free-Fly Band & Ceiling Desync (Dual Ship Impossible)
* **Severity:** Critical (Gameplay Blocker)
* **Affected Levels:** *Hexagon Force* (L16), *Clubstep* (L14), *Theory of Everything 2* (L18), *Deadlocked* (L20)
* **Files:** [`src/game/sim.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/game/sim.ts#L1007-L1016), [`src/gd/camera.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/camera.ts#L151-L172)
* **Root Cause:** When a Dual Portal (ID 286) activates, Player 2 (`dualPartner`) spawns with inverted gravity. However, Player 2 evaluates free-fly ceiling/floor bounds against Player 1's `cameraYCenter` without mirroring the free-fly band for inverted gravity.
* **Symptom:** Player 2 immediately dies on an invisible ceiling boundary in Dual Ship/Wave mode while Player 1 is completely safe.
* **Fix Instructions:**
  1. In `src/gd/camera.ts`, ensure `dualCameraBottom()` returns mirrored ceiling/floor bounds for inverted gravity (`gravitySign < 0`).
  2. In `src/game/sim.ts`, pass Player 2's mirrored camera bounds during `stepOne(dual, ...)`.

* **✅ Resolved (2026-09-22).** The real cause was the band's *anchor*, not a missing mirror (the band is symmetric, so mirroring changes nothing). Two faults, both measured on the native macros:
  1. `spawnDual` anchored on the dual portal's raw y. The game quantises it like a flying portal (`gdY < 270 → 240`, else the 30-grid). L17's corridor is symmetric about y=150, not the portal's 165; the off-centre anchor held P2 on a band floor at y=30, into the hazard at (15600, 31).
  2. Each player's own gamemode portal re-anchored its band. The native P1 in L16's dual ship flies exactly 255..525 = 390 ± 135 (the dual anchor) while crossing a portal whose own centre is 450. Inside a dual, gamemode portals now keep the dual's anchor (`sim.ts`).
* **Verification:** Blast Processing's native replay no longer loses P2 at x=15593 — it now runs to x=22964. Every dual frame in the macros now sits inside its band (DUAL ship FLIP was reaching −195).

### [x] [BUG-02] Wave Mode Front-Wall Slope Clipping ("Wave Immune to Slopes")
* **Severity:** High (Gameplay Physics)
* **Affected Levels:** *Deadlocked* (L20), *Geometrical Dominator* (L19), *Blast Processing* (L17)
* **Files:** [`src/game/collision.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/game/collision.ts#L355-L395), [`src/game/sim.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/game/sim.ts#L747-L755)
* **Root Cause:** When the Wave mode collides with a slope tile, `resolveSlope()` snaps the Wave's Y position onto `slopeSurfaceY()` without checking whether the Wave's velocity vector impacted the **vertical front/cliff face** of the slope tile.
* **Symptom:** The Wave passes straight through solid slope front walls like a ghost instead of dying on impact.
* **Fix Instructions:**
  1. In `src/game/collision.ts`, check if the Wave's X bounding box impacts the vertical entry face of the slope collider (`slopeUphill` face check).
  2. If the Wave impacts the vertical cliff face without moving parallel/upward along the hypotenuse, trigger `die(s, "wave-solid", c.id)`.

* **✅ Resolved (2026-09-22).** `hitsSlopeWall()` in `collision.ts`: a wedge whose tall end faces the player is a wall, and the wave dies on it (`wave-solid`). Parts of the wall covered by a neighbouring solid — every staircase joint — are excluded.
* **Verification:** across all 17,243 native wave frames the real wave's box never crosses an uncovered wall, so the rule cannot end a real run; the native replays are unchanged by it. Regression tests cover sliding in, climbing in, passing over, and a covered joint.

### [x] [BUG-03] Robot Mode Missing Ceiling Band (Unconfined Flight)
* **Severity:** High (Gamemode Physics)
* **Affected Levels:** *Fingerdash* (L21), *Dash* (L22)
* **Files:** [`src/gd/camera.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/camera.ts#L86-L94), [`src/gd/gamemodes.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/gamemodes.ts#L198)
* **Root Cause:** `bandFor("robot")` in `camera.ts` returns `null` (unconfined).
* **Symptom:** Holding jump in Robot mode causes the player to accelerate infinitely upwards into space or clip through block roofs.
* **Fix Instructions:**
  1. In `src/gd/camera.ts`, add Robot case to `bandFor()` returning `{ below: 135, above: 136 }`.
  2. Ensure Robot hold jump timer (`holdTime`) caps at binary-sourced `0.2778s` max duration.

* **✅ Resolved (2026-09-22) — the band half of this spec was rejected by the native evidence.**
  * The hold cap already existed: `ROBOT_HOLD_MAX = (1.5 / 0.1) / 54 = 0.2778 s`, read from the binary, so the robot cannot climb indefinitely.
  * Giving the robot the ship's `{135, 136}` band **contradicts the real game**: native robot runs go 225 below and 364 above `cameraYCenter` (L19/L20), and adding the band ended L19's native replay at x=3927 instead of x=5877. The robot stays unbanded, as in the original (`changeGameMode` has no robot case); `bandFor("robot")` returning `null` is now pinned by a test.

### [x] [BUG-04] Ball Mode & Inverted Gravity Ceiling Clipping
* **Severity:** Medium (Gamemode Physics)

### [x] [BUG-05] Missing Special Block Gameplay Mechanics (S, D, J, H Blocks)
* **Severity:** High (Gameplay Physics)
* **Affected Levels:** *Clutterfunk* (L11), *Clubstep* (L14), *Electrodynamix* (L15), *Fingerdash* (L21), *Dash* (L22)
* **Files:** [`src/game/sim.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/game/sim.ts), [`src/gd/interactives.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/interactives.ts), [`src/gd/gamemodes.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/gamemodes.ts)
* **Missing Logic & Fix Instructions:**
  * **S Block (1829 - Dash Stop):** Touch collision must immediately clear active `player.dash` state (set `player.dash = 0`).
  * **D Block (1751 - Wave Block Touch):** Touch collision must grant Wave mode immunity against solid block death.
  * **J Block (1813 - Disable Auto-Jump):** Touch collision after an orb must set `player.queuedHold = false`.
  * **H Block (1859 - Head Bump Safety):** Cube/Robot head collision against ceiling blocks must prevent fatal death when covered by H-blocks.

* **✅ Resolved (2026-09-22).** New interactive kind `special` (`SPECIAL_BLOCKS` in `collision.ts`), read against the full box before solids resolve. The semantics match the 2.2 player state flags named in the Geode bindings (`m_stateNoAutoJump`, `m_stateDartSlide`, `m_stateHitHead`, `stopDashing()`):
  * **S (1829)** — `stopDash()` on first contact (the gravity dash flips as it ends, as on release);
  * **D (1755, not 1751)** — the wave slides along solids ship-style instead of dying;
  * **J (1813)** — a held button no longer auto-jumps off the ground; a fresh press still does;
  * **H (1859)** — a head hit on a solid is a bump for every mode.
* **Correction:** **1751 is the gravity dash orb (`dashRing_02`), not the D block — the D block is 1755.**
* **Verification:** Fingerdash's native replay is now frame-exact through the S and J sections (first drift x=2719 → x=5978) and survives to x=12190 (was x=3416). S is confirmed frame-exactly: the real dash ends on frame 2088, the first frame the box reaches the S column.

### [x] [BUG-07] Background Parallax Scroll Speed is 2x-4x Too Fast
* **Severity:** Medium (Visual Game Feel)
* **Affected Levels:** All 22 Main Levels
* **File:** [`src/scenes/levelScene.ts:32`](file:///Users/stas/projects/geometry-dash/web-port/src/scenes/levelScene.ts#L32)
* **Root Cause:** `BG_PARALLAX` is set to `0.2` (native GD is `0.05` to `0.1`).
* **Symptom:** Background scrolls franticly fast during gameplay.
* **Fix Instructions:**
  1. In `src/scenes/levelScene.ts`, change `const BG_PARALLAX = 0.2;` to `0.08` or `0.1`.

* **✅ Resolved (2026-09-22) — the formula was wrong, not just the constant.** The background is drawn through the world camera and was anchored at `-camX * 0.2`, i.e. moving the *other* way: it scrolled at **1.2×** the level, and 0.08 would still have given 1.08×. Tiles now follow the camera by `1 − f`, so they appear to move at `f`.
* **`f = 0.1` on both axes, read from the binary:** level setup calls `GJBaseGameLayer::updateBGArtSpeed(0.1f, 0.1f)` (m1 `0xc37d8`), and `updateCameraBGArt` (m1 `0x12a788`) shifts the art by `cameraDelta × mod × zoom`. The vertical axis also parallaxes now (it was fixed in the world). Pinned by `tests/background.test.ts`.

### [x] [BUG-08] Unparsed Level Header Backgrounds (`kA6`) & Grounds (`kA7`)
* **Severity:** Medium (Visual Parity)
* **Affected Levels:** All 22 Main Levels
* **Files:** [`src/gd/level.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/level.ts#L50-L88), [`src/scenes/levelScene.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/scenes/levelScene.ts)
* **Root Cause:** `level.ts` only parses `kS` color keys and ignores `kA6` (Background ID) and `kA7` (Ground ID) from level headers.
* **Symptom:** Every level renders with the exact same default background and ground texture pattern (e.g. *Clubstep* lava ground and *Electrodynamix* grid background do not load).
* **Fix Instructions:**
  1. Parse `kA6` and `kA7` in `parseLevelString()` into `Level.bgStyle` and `Level.groundStyle`.
  2. Update `levelScene.ts` to select the matching background and ground texture sheets based on `bgStyle` and `groundStyle`.

* **✅ Resolved (2026-09-22).** The premise was partly stale: `levelScene.ts` already read `kA6`/`kA7` from the raw header, and the assets load for all 22 levels. Levels 1–14 genuinely store `kA6=0, kA7=0` — art 01 in the game too — so they are *meant* to share the default. Clubstep does not have a distinct background in its header. The parse now lives in `parseLevelString()` as `Level.bgStyle` / `Level.groundStyle` (0 read as 01), and the scene uses those; a test pins every distinct pair (L15 2/2 … L22 25/17) and that its art exists.
* **Not covered:** the 2.2 middleground (`kA25`, used by L22) is still not drawn — a separate feature.

### [x] [BUG-09] Hardcoded Colors on Decorative Slope Children
* **Severity:** Low (Visual Polish)
* **Affected Levels:** *Theory of Everything*, *Electroman Adventures*, *Hexagon Force*
* **File:** [`src/gd/objects.ts`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/objects.ts#L837-L848)
* **Root Cause:** Slope definitions (IDs 1743, 1744, 1746, 1758, 1759) have hardcoded child RGB values (`r: 150, g: 255, b: 255`) instead of dynamically inheriting the level's `COL1`/`COL2` color channels.
* **Fix Instructions:**
  1. Replace hardcoded RGB values with dynamic color channel references (`color: "base"` or `"detail"`).

* **✅ Resolved (2026-09-22).** The children already used channel slots (`base`/`detail`); the hardcoded RGB was the *fallback* tint for an unset channel, where the parent falls back to white. Those five slopes' children are now neutral white (in `objects.ts` and in `gen-objects.mjs`), so parent and child stay on one colour. **Note:** these ids only occur in L21/L22 (not ToE/Electroman/Hexagon Force), and every channel they use there is defined, so the change is invisible in the 22 levels.
* **Investigated and deliberately not shipped:** binding *every* sprite to its channel even when the header omits it (1005–1012 and trigger-only channels). It visibly changes art in L13/L15/L19 (the L19 rainbow loses its ROYGBV bands), and without a native capture to adjudicate it, it is not safe to ship.

## ⚡ Optimization & Engine Fixes

### [x] [BUG-10] O(N²) Collision Pair Hash Overflow for Block IDs >10,000
* **Severity:** Medium (Engine Stability)
* **File:** [`src/gd/triggers.ts:35-50`](file:///Users/stas/projects/geometry-dash/web-port/src/gd/triggers.ts#L35-L50)
* **Root Cause:** Collision block pair keys use `lo * 10000 + hi`.
* **Risk:** When custom or heavy 2.2 levels contain block IDs $\ge 10000$, pair keys collide in the map.
* **Fix Instructions:**
  1. Update `pairKey(a, b)` to use string key `${lo}_${hi}` or Bit32 hash `(lo << 16) | hi`.

* **✅ Already fixed before this sprint.** `pairKey` packs with a 2²¹ shift (`lo * 2**21 + hi`), exact as a double for any editor id — the `lo * 10000 + hi` form is gone. The suggested `(lo << 16) | hi` would have been a regression (aliasing at 65,536, negative keys from `lo ≥ 32768`). A new test round-trips ids across 0…2²¹−1 and checks every pair's key is distinct.
